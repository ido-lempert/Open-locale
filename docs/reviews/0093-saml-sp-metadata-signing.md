# 0093 - SAML SP metadata endpoint + AuthnRequest signing

Slice 27. GET /auth/saml/metadata serves the SP descriptor (entity ID, ACS,
signing certificate when configured), and AuthnRequests are signed per
SAML Bindings 3.4.4.1 (HTTP-Redirect binding) when SAML_SP_PRIVATE_KEY /
SAML_SP_SIGNING_CERT are set.

## Pass 1 - Developer
- Signing is library-built (node-saml signs the URLSearchParams serialization
  of SAMLRequest[, RelayState], SigAlg with the SP key) - no signature math
  in app code; the mock's VERIFIER uses node:crypto only.
- PEM env values accept literal \n-escaped form (normalized before use).
- Metadata generated by the library's generateServiceProviderMetadata with
  the configured signing cert; no decryption KeyDescriptor (no decryption
  key configured this slice - honest advertisement).
- Signing is config-gated: no key -> unsigned requests, exactly as before
  (some IdPs don't require signed requests).

## Pass 2 - PM
- Two more SAML follow-ups closed (metadata endpoint, SP request signing).
  Remaining: OIDC/SAML store unification, settings UI.

## Pass 3 - Designer
- No UI surface; the settings-UI follow-up will expose "download SP metadata".

## Pass 4 - Security
- Metadata is public by design (it contains no secrets - entity ID, ACS URL,
  public cert) and mirrors what every IdP-facing SP publishes.
- Request signing is proven end-to-end at the transport boundary: the mock
  IdP verifies the redirect-binding signature with the SP cert (valid ->
  'valid'), and a tampered Signature value -> 'invalid' (discriminating leg -
  the signature is not decorative).
- Signing does not weaken validation: InResponseTo issuance/consumption and
  every ACS-side check are unchanged; the suite's 41 legs all pass with
  signing enabled, including every negative leg.
- The SP private key arrives only via server env; it is never logged, never
  returned by any endpoint, and metadata advertises only the certificate.
