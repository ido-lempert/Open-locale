# 0095 - Bind SAML linking to its exact AuthnRequest

## Developer pass
Found an app/security defect: link state named an account and authEpoch, but
not its AuthnRequest. A response to another valid outstanding request could
be combined with a link token. Bind the opaque token to the exact request
ID generated by node-saml. Parse only the SP's own deflated request for that
ID. Recheck capacity after the asynchronous generation step.

Keep a bounded request-purpose tombstone until the request TTL, even after
link token consumption. Removing RelayState cannot turn a linking response
into ordinary provisioning, including repeated submissions after rejection.
The two link maps prune on start, remain process-local, and lose state on
restart. This is single-instance groundwork, not distributed SSO support.

## Product pass
Keep plain SAML login separate from account linking. A mismatch burns the
link token; the user must restart the flow. Fix outdated collision text that
still claimed linking was unimplemented. Existing configuration editing and
shared OIDC/SAML stores are implementation choices, not permission gates.

## Designer pass
API-only. No changed visual surface or new screenshot required.

## Security pass
Both Response and Assertion signatures remain required. Precheck reads the
Response InResponseTo and checks request purpose before any database write;
node-saml still validates the signatures and consumes the request before
identity processing. The library's getVerifiedXml verifies a single #ID
reference resolving to exactly one node AND requires that node to be the
signature's parent (xml.js), before returning signedReferences. This is the
binding evidence, not an assumption based only on element count.

Purpose records survive consumed tokens until request expiry to avoid a
strip-and-retry downgrade. No new cryptographic implementation or provider
registration. No blanket security-completion or external-IdP claim.

## QA/integration pass
SAML suite: 51 PASS (was 42). Nine added checks: different valid request
rejected with exact mismatch reason; no identity/user created; mismatch burns
token; stripped RelayState rejected; no user created; repeated stripped
response rejected; consumed token retains purpose tombstone; live authEpoch
change rejected after valid signatures; no stale binding created.

Corrected the happy-link and cross-account-steal fixtures to answer their
actual start-link requests. They previously used unrelated fresh requests,
which hid the defect. This is an APP/SECURITY fix plus fixture corrections,
not a test-only fix. Both targeted runs passed (49, then 51 checks as repeat
stripping guards were added). API build RC=0; API unit 135 PASS RC=0; docs
consistency 4 PASS RC=0. No changes to UI or OIDC implementation.
